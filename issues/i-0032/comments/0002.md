Committed on `agents/i-0032` at `ee85079`, published as a checkpoint rather than flagged for review — the `taste-app` half of the gate cannot run on this machine right now (see the bottom of this comment, and i-0040).

**The issue's diagnosis was half right, and the other half is where the 255 actually came from.**

The stated shape — "somewhere between `podman start` returning and `podman exec` being willing there is a window the supervisor does not account for" — is real and is now closed. But it is not what produced the failures on record. This environment's own lifecycle log says so:

```
container started: 689a6f0d2c10…
git identity inherited from host: David Strauss <david@davidstrauss.net>
$ podman build -t taste-img-65b27bd1cc96 …          ← a second, whole lifecycle run
…
container started: b89ec811c4fa…
git identity inherited from host: David Strauss <david@davidstrauss.net>
```

**Two `container started` lines for one start.** `start_issue_environment` (window.rs) spawns `Supervisor::reload`, and three lines later, on the same thread, builds the chat and calls `activate()`. The chat's gate asks its environment whether a run is on its way — and the spawned task has not been polled yet, so the state machine still reads `ConfigDetected`, `in_transition` is false, `revive_wanted` is true, and the gate returns `StartThenHold` and starts a **second** lifecycle run. The `lifecycle` mutex then does exactly the wrong thing correctly: it makes the second run *wait* rather than not happen. The first run finishes, aims the exec target, probes hosting, publishes `Running`; the chat spawns its agent into the container; the second run acquires the mutex and `podman rm -f`s that same container out from under it. Hence:

```
03:10:14 INFO taste_ide::window: environment i-0032 is available
03:10:17 INFO taste_ide::chat: chat i-0032: spawning its agent (resume=none)
03:10:17 INFO taste_ide::chat: chat i-0032: connection closed (Process exited with exit status: 255:
         Error: can only create exec sessions on running containers: container state improper)
03:10:39 INFO taste_ide::chat: chat i-0032: spawning its agent (resume=none)
```

Twenty-two seconds here rather than sixteen, and the whole second build in between. A readiness probe alone would not have removed a single one of those lines — the first run's container *was* ready; it was then taken away.

**What changed.** Both halves, because "available" has to mean both "an exec would land" and "nothing is about to take it away".

1. `Supervisor::await_exec_ready` — after `podman run -d`, before the `ExecContext` is aimed and before `Running` is published. Bounded at **10 s** with a doubling backoff (25 ms → 500 ms cap), and on exhaustion it **logs one line and carries on**, aiming and announcing exactly as before. The trap the issue and the triage both named is the whole reason that fallback is there: nothing downstream needs the guarantee, so a container that is never going to run costs ten seconds once and then behaves as it always did. The check is `podman container inspect --format {{.State.Running}}`, not `exec … true` — it asks podman for the predicate `podman exec` itself checks, costs one control-plane round trip, and needs nothing of the image (an exec probe would report "this image has no `true`" as "this container is not ready"). Skipped entirely when the IDE is self-hosting; the rung with no podman never reaches it, since it runs after a `podman run` that succeeded.

2. `Supervisor::lifecycle_wanted` — a count of runs **asked for**, raised by the new `Supervisor::request_reload` *before* the task exists and lowered by a guard however the run ends (error, early bail, panic, or a task dropped before it was polled — a count that never comes down would be an environment forever "on its way", which is worse than the duplicate run). `Supervisor::in_transition` is now the one predicate for "something is already bringing it up": the claim, plus `Building`/`Starting`. Both places that *start* an environment go through `request_reload`; an explicit Rebuild (fleet row, banner, `devcontainer_reload`) deliberately does not — a person asking again means it.

**Expected log shape after this.** One `container started:` per start, one `spawning its agent`, no `connection closed`, no `exit status: 255`, and the agent's first spawn is the one that reaches `Ready`.

**Tests.** `the_readiness_wait_is_bounded_and_backs_off` pins the bound as a readable schedule (sums to exactly the budget, caps, terminates for a budget smaller than one step). `an_environment_is_on_its_way_from_the_moment_a_run_is_asked_for` pins the claim being visible while the state machine still says otherwise. `a_start_asks_for_one_lifecycle_run_and_the_chat_waits_for_it` (chat.rs) walks the timeline above as gate decisions, alongside i-0011's own sequence test. And `crates/taste-devcontainer/tests/readiness.rs` is the live reproduction the issue asked for — two `#[ignore]`d real-podman tests: one times an exec off the `Running` announcement on the event bus, the other calls `request_reload` twice on one thread and asserts one `container started:` line and a container still there afterwards.

**What did not run, and why.** The host volume is **full** — 466 MiB free of 930 GB at the time of writing, 8.6 GiB under the IDE's own floor, and podman is now failing to write its own container state. `cargo fmt --all -- --check` passes workspace-wide; `cargo clippy` and `cargo test` pass for `taste-core` and `taste-devcontainer` (the seven `configwatch` inotify failures are i-0030, pre-existing and unrelated). **`taste-app` could not be compiled at all**, so its three edits — the `environment_in_transition` delegation, the `start_container` rewrite, and the new gate test — are unverified by the compiler. The first build of that crate in a fresh clone is tens of gigabytes and there is nowhere to put them; the failure arrives as `cc` exiting non-zero with no message, which is why I filed **i-0040**. I will finish the gate and publish `ready: true` the moment there is space; until then this is a checkpoint.
