Done and committed as 94f9d8e on `agents/i-0030` (checkpoint publish; not yet flagged for review — see the last paragraph).

**What shipped.** `taste_core::watcher::InotifyLease`, taken at the top of every test that opens an inotify instance — five in `taste-core::watcher` (the body named three; `created_directories_get_watched` and `atomic_save_reports_the_file_as_changed` fail the same way and are fixed with them) and seven in `taste-devcontainer::configwatch`, which is the count i-0031 saw on clean `main`. It does both of the body's cheapest outcome and the comment's fourth option:

- **it queues** — a process-wide turn, so a test binary holds at most one instance at a time instead of one per test thread. This is not a nicety: the pre-change run here was five such tests against four free instances with exactly one failure, so the gate was partly red at its own hands. Since cargo runs test binaries one after another, that is one instance at a time for the whole workspace gate;
- **it skips** — `<test>: host inotify limit reached — skipped (<the existing message>)`, in the shape the GTK tests use, and only on a real `EMFILE` from `inotify_init` or an error whose text names the sysctl.

`name_the_inotify_limit` is untouched apart from taking the sysctl's name from a new `INSTANCE_LIMIT_SYSCTL` const, which is also what lets the skip recognise the condition after the `notify::Error` has been erased into an `anyhow::Error` with a `.context()` on top. Both directions of that predicate are asserted in `an_exhausted_inotify_limit_says_which_limit_it_was`, because a skip that never fires leaves the gate red and one that fires too readily hides a real failure.

README → "From stock Silverblue to self-hosting" now names `fs.inotify.max_user_instances` as the one host setting a fleet wants, at 512, with this machine's numbers.

The fleet-wide notice (the body's second outcome) is filed as **i-0035** rather than done here.

**Gate.** `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace` are all green in this environment, with the twelve tests reporting skipped.

**One reading still owed.** The other half of the verification — the same tests running their assertions on a host with room — cannot be taken here: sampled every 30s from 02:05 to 02:17 with four environments live, the host had `free: 0` every time, so not one instance was available to anyone. No sudo in the devcontainer and a nested user namespace charges the same host uid, so there is no honest way to manufacture headroom from inside. A run is armed to fire the moment the host frees two instances. Raising the sysctl is what would settle it immediately.
