Done, on `agents/i-0025` (5 commits on top of `d472923`). The decisions the issue asked to be argued:

**Which mechanism.** Mechanism 1 only — the IDE holds the policy and answers for every chat. Mechanism 2 (`.claude/settings.json`) is *not* built, and the argument is written into ARCHITECTURE → Permissions where the next reader will ask. Four reasons: it is one client's file and the abstraction here is ACP; it arrives late (a running environment would not see it until `update_from_main` and a respawn, a new one only at clone time, where the IDE's own answer is in force at the click); it is a commit the user did not make, in tracked files; and it puts the project's permission policy inside the checkout, which is the one thing an agent can write — `write_allowed` bounds writes *through* the IDE, and in container mode `ide_exec` is a shell with the workspace writable, so the file saying what the agent may do would be a file the agent may widen. What protects the book instead is that it is not reachable at all: it lives with the rest of the workspace's state under `$XDG_STATE_HOME`, outside every checkout, and the only code that writes it is a card's click handler. Written as a weighing rather than a closed door — the two are not exclusive, and the condition for revisiting (per-call round-trip latency) is named.

One fact from this repo decided it: an agent's cwd is a read-only stub (`sandbox::ensure_workspace_stub`, `policy::agent_context_scope`), so an agent's own "don't ask again" cannot persist into the project *at all*. The durable, project-wide half was never going to be the agent's.

**Grain.** The tool, and only the IDE's own — `taste_mcp::protocol::effect` is a judgement about this server's tools, not GitHub's. A standing **yes** is refused for anything `Destructive` (a blanket yes to `ide_exec` is a shell with no gate) and for a `requiresUserInteraction` tool (a server may not keep one behind the client's back). A standing **no** is refused for nothing: refusing is never a widening. That is the asymmetry and its reason. An agent's own tools are keyed on nothing — a `Bash` call's title is the command, which is the agent's grain to hold.

**`RejectAlways`.** Grows with the other side; `card_options` covers all four kinds.

**Where the third answer goes.** Visible buttons in an `AdwWrapBox`, not a split button or a menu — a standing answer hidden behind a disclosure would be dropped a second time, more politely. Order is refusals left, approvals right, each standing answer just outboard of the one-shot it strengthens, so the suggested yes stays rightmost and the everyday two-option card does not move. Measured: the chat pane's minimum is still 320 across the whole ladder, and the four-answer card wraps to two lines at the narrow rung.

**Seeing and undoing.** The settings shade lists what the project has settled with an undo per row — and since the answers are the project's, the coordinator's own shade revokes one given in any environment, so nothing here scales with the fleet.
