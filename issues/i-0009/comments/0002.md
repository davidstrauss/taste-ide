Confirmed as a separate defect, left unfixed per scope: destroying an environment unconditionally wipes its persisted review verdict, even when its branch of record survives with unpublished-to-main commits.

The mechanism: `console.rs`'s destroy flow (~line 2506) calls `forget_environment`, which `state.rs::forget_environment` (line 216-219) implements as an unconditional `retain` that drops the environment's entire `WorkspaceState` entry — including `review` and `review_since` — regardless of what state it was in. `ReviewBoard::forget` (review.rs:267-277) mirrors this by dropping the in-memory cache entry too, with a comment noting the state-file entry is already gone "wholesale."

But destroying a clone only removes the container, image, volumes, and local working copy (`registry.rs::destroy`) — it does not touch `agents/<env>` in the user's main checkout, which is where `publish` already moved any committed work. So an environment that was `FlaggedForReview` (or even `Merged`/`Rejected`) before being destroyed loses that verdict the moment it is forgotten. `review_list`'s first loop then finds the still-existing branch via `git.env_branches`, looks up `self.workspace.review.state(&id)`, gets the default (`ReviewState::Working`, since "unknown environments are Working: absence of a flag is not a state of its own" — review.rs:200-201), and reports a settled or flagged environment's branch back as plain `working` — indistinguishable from one nobody has ever looked at.

This is a different gap from the one this issue fixes: that one was about a `Working` environment that never published anything being invisible; this one is about a branch that publish already made visible losing its recorded verdict once its environment is destroyed. Not fixed here, per the boundary this issue's task drew.
