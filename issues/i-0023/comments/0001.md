Fixed on `agents/i-0023`, two commits. It was neither candidate exactly, and the backtrace settled it rather than reasoning.

**What it is.** `TASTE_LOG_BACKTRACE=1` (new, see below) caught the CRITICAL with its stack: `populate_async` on our `CommandProvider` → `set_proposals_for_provider` with a NON-empty model → the context's `notify::empty` → `display_show` → `gtk_widget_show` → `gdk_popup_present` with width 0. So the popup being presented empty is one that legitimately had proposals — upstream shows it before its rows exist. What made that happen dozens of times a session is ours: `matching` trimmed an *optional* leading slash, so interactive completion (which asks about every word, not just slash commands) pulled the command list up over ordinary prose. "**c**ontainer", "**c**lone", "**c**omes" all prefix `compact`, `context` and `clear`. `is_trigger` has always said the rule — a slash, at the very start of the box; `populate` and `refilter` now go by it too, through `command_prefix`.

The earlier guard (e8c7945: no matches is an error, not an empty page) covered ordinary words matching NOTHING. It could not cover the ones that match something, and in English those are common.

**The candidates, checked rather than assumed.**

1. `refilter`'s `set_proposals_for_provider(..., None)` route — not it. That route is what *closes* the popup and is correct; the CRITICAL arrives through the populate path with a non-empty model, which the stack shows plainly.
2. Dispatch sharing the chat pane's `CommandProvider` — true as a description of the code (`chat.rs:1442` and `compose.rs:529` register the same instance), but not the cause, and not a fault. A provider carries no per-completion state: everything the framework tracks lives in the `GtkSourceCompletionContext`, which is per-completion. The chat's own entry is also `set_visible(false)` (`chat.rs:1438`), so nothing is ever typed into it and its completion never starts a context. Left alone.

**Numbers, same binary, five runs each.** Typing `/co`: 0 criticals, 5/5. Typing "Relocation waits for the container and the clone comes up": 2 criticals, 5/5. After the fix, 0 for both, and 0 on longer bursts.

**The gate.** `build-aux/headless/typing.sh` — Xvfb, a session bus, `G_DEBUG=fatal-criticals`, and `TASTE_PROBE_TYPE` typing into Dispatch a character at a time (typing is not the same act as setting the text; the completion, the tooltips and the popup's own frame clock all live in the gaps). Before: exit 134. After: exit 0, three runs out of three. `cargo fmt`, `clippy -D warnings` and `cargo test --workspace` all clean.

**The list still opens, filters and closes**, and that is asserted rather than eyeballed: the (ignored, display-needing) test in `command_completion.rs` reads the popup's own rows — a bare slash offers all four commands, `co` narrows to `/compact` and `/context` with the other two gone, `zz` closes it. `activate` is untouched by either commit, so applying a completion is unchanged. "Both composers" turns out to be one: the chat pane's own field is the hidden one above.

**A second defect, found while confirming that half — fixed in its own commit.** `is_trigger` asked for `iter.offset() == 0`, reading `iter` as the slash's position. It is not: the framework asks after the insertion, caret one past the typed character, so the offset is 1 and the test could never be true. The trigger never fired. The list only ever appeared because the ordinary-word path picked it up on the NEXT character — the path the first commit closes — so without this the slash would have stopped opening anything at all. Opening a keystroke earlier is one more popup per command, so it was measured, not assumed: clean.

**What is left, and it is not ours.** The upstream race is still there — gtksourceview presents the completion popup from a `notify::empty` handler before the list has rows. We no longer provoke it, because the only popups we open now are ones a person asked for by typing a slash, and those come back clean over many runs. If it ever reappears on the slash path itself, the fix would be a minimum width on the completion list rather than another guard here. Say the word and I will file that as its own issue.
