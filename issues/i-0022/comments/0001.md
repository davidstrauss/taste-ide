Done and on `agents/i-0022`, two commits. The two design questions the issue raised, decided:

**Who forgets — the event, and nothing else.** `EnvironmentRegistry::destroy` already publishes `Event::EnvironmentRemoved`, and `window.rs`'s arm for it already forgot the chat and the editor's stowed tabs. The console's share of the fan-out moved there as `Console::forget_environment`, and `run_destroy` stops forgetting anything (it keeps only the toast and closing its own intervention card — closing that from the shared handler would shut an unrelated question an agent's destroy happened to interrupt). So the MCP path touches no widget, which is not a concession: GTK objects never leave the main thread, so it could not. It also answers the awkward case for free — a destroy requested while the panel has that row selected comes home to `primary` on the main thread like any other selection change.

**What replaces the dialog — the same facts, as data, and `force` is not the last word.** The tool enumerates what `destroy_intervention` enumerates (unpublished branches with counts and summaries, dirty file count) and refuses with it, the way `issue_update`'s completion gate refuses on facts. `force: true` says the caller read it — and on that path the IDE asks the user, in the same rendering (`at_stake_lines` feeds both the agent's refusal and the user's prompt, so the agent cannot relay different facts from the ones the dialog shows), failing closed when there is nobody to ask.

On the permission question you asked me to settle: **yes, but narrowed the way `devcontainer_reload` is.** The reload asks only when the config has *drifted*; these ask only when something would actually be lost. A reclaim of a merged environment — the case the tool exists for — goes through in one call with nobody interrupted. That is what keeps ENVIRONMENTS.md's "no user prompt per creation" and this prompt from contradicting each other: a creation's prompt would always be answered yes, this one is genuinely in doubt. Both tools also carry `_meta["anthropic/requiresUserInteraction"]`, so a client in auto mode cannot have its classifier answer first.

**Both are coordinator-only**, for the reason starting is: a worker removing a sibling's world, or deleting the issue it was told to argue with, is what the socket split exists to refuse.

Refusals implemented, each with a test: the primary; the caller's own environment; an unknown id; unpublished work without `force`; `force` with the user saying no; an issue whose environment still exists (named, pointing at `environment_destroy`); an issue carrying a resolution, comments, links or a claim without `force`. Plus the reclaim that asks nobody, and the approved destroy — which also asserts the claim came back to the queue with its comment, and that **exactly one** `EnvironmentRemoved` goes out. That last property is asserted again in `taste-devcontainer`'s registry test, which is where both callers share the publish and so where it can regress.

Docs: `ENVIRONMENTS.md` gains the removal half in the coordinator's tool list plus three paragraphs after "no user prompt per creation" (who forgets, what replaces the dialog, why `force` is not the last word); `ARCHITECTURE.md`'s coordinator bullet now says five tools, not three; `issue_list`'s note names `environment_destroy` as the thing that gives the disk back, beside the sentence saying stopping does not.
