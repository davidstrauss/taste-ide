## The four sites that move together, by function

Read against `2ec85b0`. Five functions, not four: the aim is where the values are *computed*, and the outside-confined spawn is where the aim's value is turned into a mount, so I name both rather than collapse them.

1. `taste_acp::aim::AgentAim::new` (`crates/taste-acp/src/aim.rs:88`) — computes `home_volume` from `environment::env_home_volume`. The aim knows the environment and *not* the agent, which is the first structural fact: an identity keyed by `(workspace, agent)` cannot be a field of a value that has no agent in it. It is computed at the seam that has both — `AgentClient::spawn_aimed`, which takes `spec` and `aim` together (`session.rs:208`).
2. `taste_acp::sandbox::container_agent_args` (`sandbox.rs:436`, reached through `container_agent_command`) — the outside-confined agent container; the site that actually writes `-v <home_volume>:/home/agent`. Fed by `AgentClient::spawn` (`session.rs:354`).
3. `taste_acp::session::login_command` (`session.rs:1499`) — the auth terminal. Outside-confined **always**, even for a relocated chat (Phase 3's asymmetry), and it goes through the same `container_agent_command` with `tty: true`. This is the only site whose *purpose* is to write identity.
4. `taste_acp::relocate::relocated_agent_command` (`relocate.rs:159`) — carries **no mount at all**, and that is the load-bearing detail rather than an omission: `podman exec` cannot add one. Its obligation is discharged entirely by (5), which is why (5) must mount every known agent's identity volume and not the one the current chat happens to use — a chat switches agents without restarting its container.
5. `taste_devcontainer::supervisor::Supervisor::ide_mounts` (`supervisor.rs:1337`) — the environment's own container. Adding to it changes the config hash by construction, so every running container goes stale the first time this ships, which is the designed behaviour and not a regression to apologise for.

A sixth path exists and needs nothing: `sandbox::wrap` (`sandbox.rs:544`), the no-podman rung, has no volumes at all — it binds the user's real `~/.gemini` and `~/.copilot` back into a tmpfs home. Identity there is already the user's own and already fleet-wide. The rung below every container is the one place this issue's problem never existed.

## The shape: a split, and why not one volume

Taking the issue's invitation to argue the other way first, because the case for a single shared `(workspace, agent)` home is better than the existing comment in `env_home_volume` admits. Its stated fear is "N agents writing one home concurrently" — but every one of these CLIs is built for exactly that: one home, many projects, several concurrent invocations. Conversation state is already namespaced by project path (`~/.claude/projects/<flattened-cwd>/`, Gemini's per-project `tmp/`) or by session id, and our environments are many projects at distinct paths. Concurrency alone does not settle it.

What settles it is ownership, and it is in-repo and concrete:

- `Supervisor::env_volumes` (`supervisor.rs:1923`) makes the home volume something an *environment owns*, `remove_volume` (`:1943`) refuses to touch a sibling's, and `disk_usage` bills it to that environment against `MAX_ORCHESTRATED_DISK_BYTES`. One shared home guts all three: destroying an environment could not reclaim its own history, and the fleet view could not attribute a byte of it.
- The one genuine race is a singleton config file rewritten wholesale (`~/.claude.json`). A human with two terminals loses a little state to it by accident; six environments is losing it by design.

So: **split**, and the conversation home is not re-keyed at all. `env_home_volume` keeps its name, its contents, and its comment.

The split line is declared per agent, in `taste_core::policy` beside `agent_context_scope` — which is already exactly this kind of per-agent home-path table, in exactly this crate, for exactly this reason (`taste-devcontainer` cannot read `taste-acp`'s registry, and site 5 needs the table). One directory per agent, `Option<&'static str>`, because a volume mounts as a directory and two paths would need two volumes:

- `gemini` → `.gemini`, `copilot` → `.copilot`. Neither CLI separates its credential from its other state at any directory boundary; that is the CLI's shape, not ours, and what makes sharing it safe is the other half of the same shape — built for one home and many projects. The registry already declares these as the auth directories (`registry.rs:139,159,174`), so no new file-layout knowledge is introduced and nothing parses a format.
- `claude-code` → **none**. Its credential never enters a container (the auth proxy), i-0036 scoped its file to the project, and the issue scopes Anthropic out. So `~/.claude` — the history, and the memory directory — stays per environment exactly as CLAUDE.md commits, and the `.claude.json` race above is avoided by never sharing it.
- `.npm` stays per environment: a cache, not an identity. (That N environments each re-download the pinned adapter is a real cost and a separate issue; I will file it rather than widen this one.)
- A user-defined agent gets no identity volume. Convention over configuration: a new agent adds a line to the table.

Volume name: `taste-id-<workspace-key>-<agent>`, derived in `taste_core::environment` with every other podman-visible string, agent id sanitized as `env_config_volume` sanitizes a declared name. Per workspace and not per machine, following i-0036: one project's credential is not another's.

## The mid-turn re-login, decided

**The second environment sees the new identity the next time its CLI reads the file, and is told nothing by the filesystem.** One volume, mounted read-write everywhere, no snapshot, no copy, and no lock. Last write wins, deliberately.

The reason it is not a lock is that these CLIs already rotate this file without being asked: an OAuth access token is refreshed from its refresh token roughly hourly, by whichever environment's agent noticed the expiry first. Any design that made a *re-login* atomic or environment-scoped would have to make that hourly *refresh* so too, and would then be N environments racing on one refresh token with N copies diverging — the failure this shape avoids rather than causes. A re-login is convergent: what it writes is strictly newer than what anyone holds.

What the loser of the race holds is therefore a **stale in-memory token, never a corrupted file**, and it surfaces as the CLI's own auth error on its next request, which the chat already renders and already turns into a sign-in affordance. Read-only mounts for non-signing environments were considered and rejected for the same reason: they would break the hourly refresh, which is a write the agent must be able to make.

One thing the IDE adds on top, because "your turn failed for no visible reason" is the bad version of this: when a sign-in completes for agent A in environment X, every other chat of this workspace on agent A gets a meta line saying the identity changed under it. Convergence is the mechanism; the sentence is the courtesy. If that plumbing turns out to be larger than the rest, it is the part I will drop and say so, not the part I will half-build.

## Orphans

The re-key this issue was filed as would have orphaned every home volume. The split orphans **no volume**: nothing is renamed. What it does orphan is *content inside live volumes* — the `~/.gemini` a user already signed into in one environment is shadowed by the new mount, so one more sign-in is needed, once, fleet-wide. Alpha posture (ARCHITECTURE → Compatibility): documented, not migrated.

The precedent still gets honoured, against a real leak that already exists: `reconcile::sweep_legacy_resources` sweeps containers and images and **never looks at volumes at all**, so this workspace's previous-generation `taste-env-<previous-key>-<env>-home` volumes, and the single-environment scheme's machine-global `taste-agent-home`, are leaked silently today. The sweep grows a volumes pass that **reports and does not remove** — the split the issue asks for ("never silently leaked and never silently deleted"), and the right asymmetry: a container and an image are rebuildable, a home volume is somebody's conversation, so its removal is the user's call, as `remove_volume` already treats it.

## Found along the way, to be filed separately, not fixed here

The outside-confined login container is pinned to **local** podman by an explicit comment (`sandbox.rs:407`), while an environment's container may live on a `podman machine` (`substrate.rs`). Named volumes do not cross that boundary: the same name is two different volumes. So on a machine substrate the auth terminal already signs in to a volume the relocated agent never reads — and Phase 3's premise, "the home is the same volume in both topologies", holds only when the substrate is local. This issue inherits the asymmetry exactly (the identity volume sits beside the home volume at each site, so it is neither better nor worse), and I will file it rather than widen this change into the substrate.
