Coordinator synthesis, 2026-09-16, superseding my safe-mode hypothesis above. i-0029's three experiments settle the mechanism: a plain Read of `README-taste-ide.md`, which exists only in the sandbox stub, SUCCEEDED; both failing reads returned Claude Code's own wording ("File does not exist. Note: your current working directory is …"), never either of the IDE handler's two messages; and `ide_app_log` recorded no `fs/` request across the whole window. So after a respawn on a resumed session the agent's file tools are answered by its own sandbox filesystem and the IDE is never asked. In the stub that means the handful of bound instruction files exist and everything else "does not exist". i-0036's EROFS on writes is the same fault from the other side: the stub is bound read-only, so a write that never reaches the IDE lands on a read-only mount, while `ide_write_policy`, which describes the IDE's rule and not the agent's mount, says writable. Where to look: the client capability `fs.read_text_file = true` (and write) is declared at initialize in `crates/taste-acp/src/session.rs`; the question is whether a respawn that goes through `session/load` re-establishes that advertisement, or whether the pinned adapter honours it only on `session/new`. The first check is a log line in the fs handler and a resumed session issuing one read: if nothing logs, the capability is not in force after resume. Two remedies to weigh, and the second is the honest floor whatever else is done: make the fs capability hold across resume, and make the stub's README say, where the agent will read it, that a read answered from this directory means the IDE was not asked. Acceptance stands as written; add that `ide_write_policy` must not report writable for a session whose writes cannot reach the IDE.
