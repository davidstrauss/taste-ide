## The proof, and it moves the mechanism one step further back (i-0027, 2026-09-16 ~03:15 UTC)

The respawn does not lose the fs capability. **The pinned adapter never uses it.** Fresh sessions "work" only because the agent is relocated into its environment's devcontainer, where its native Read/Write/Edit find the real checkout bound at its host path. Any spawn that lands OUTSIDE a container (the sibling agent container, or bwrap) gets the read-only stand-in workspace, and there the native tools see `CLAUDE.md`, `README-taste-ide.md`, and nothing else.

### 1. The adapter's source

In `@agentclientprotocol/claude-agent-acp@0.73.0` (the registry pin), `dist/acp-agent.js` defines `readTextFile`/`writeTextFile` wrappers around the client's `fs/*` methods, and nothing in `dist/` calls them. No file consults `clientCapabilities.fs`; there is no `mcp__acp__Read`, and no `mcp-server.js` at all. `docs/ROADMAP.md` line 141 already records exactly this ("one assumption under it is false … nothing calls them; Claude Code reads the filesystem directly"), and chose relocation (option C) as the answer, keeping the outside rung "as the rung of last resort".

### 2. A live experiment, on the documented ACP surface only

A 60-line node ACP client (`initialize` → `session/new` → `session/prompt`), run from inside this agent's own sandbox against a second copy of the pinned adapter, advertising `clientCapabilities.fs = { readTextFile: true, writeTextFile: true }` and ready to answer any `fs/read_text_file` with the text `SERVED-BY-CLIENT`. Prompt: "Use the Read tool on `<cwd>/README-taste-ide.md` and reply with only its first line."

```
[init] agentCapabilities= {… "loadSession":true …}
[update tool_call] title=Read File status=pending kind=read
[update tool_call_update] title=Read README-taste-ide.md rawInput={"file_path":"…/i-0027/repo/README-taste-ide.md"}
[update tool_call_update] status=completed
[agent] # The workspace is not here
[prompt done] {"stopReason":"end_turn", …}
[methods seen] ["session/update"]
[fs/read_text_file requests] 0
```

The Read completed and returned the stub README's real first line, not `SERVED-BY-CLIENT`. Zero `fs/read_text_file` requests. The capability was advertised on a brand-new session, not a resumed one, and it made no difference. Script to be committed as `build-aux/acp/fs-probe.mjs`.

### What this means for the acceptance

- `fs/read_text_file` will not "answer again after a restart" for this adapter, because it never answered before; the IDE's fs handlers have only ever served the fake test agent. The log line requested goes in anyway (INFO, environment + parent), and it will say, over time, exactly that.
- The real fault is the respawn TOPOLOGY: `schedule_reconnect` and the settle path (`retopologize`) bring a dead agent back outside-confined whenever its container is down ("the existing bounded reconnect brings it back outside-confined, because that is what the environment now is" — ENVIRONMENTS.md § Relocation). That was a sound rule when the outside rung had a working fs leg; it does not.
- i-0036's EROFS is the same fault one rung up: the baseline binds the checkout read-only, and writes that never reach the IDE land on that mount while `ide_write_policy` describes the IDE's rule.

### Plan (starting now)

1. **Proof in the tree**: INFO log line in both fs handlers, naming the environment and the path's parent; `build-aux/acp/fs-probe.mjs` with the recipe; the finding recorded in ENVIRONMENTS.md/ROADMAP/CLAUDE.md where the old claim stands.
2. **Fix at the respawn path**: a non-primary agent never comes back outside a container it could be inside. The reconnect and the settle path go through the same gate `activate` uses, in a flavour that never starts a container: container stopped → wait and say so (a send, the fleet's Start, or a reload brings it back inside with its conversation via `session/load`); hosting probe still pending → wait for the republish instead of spawning outside first; failed/no podman → outside, as today. Pinned by unit tests on the gate.
3. **Floor**: the stub README says, first thing, that a read answered from that directory means the IDE was not asked and why; the MCP instructions stop claiming fs mediation for this adapter; `ChatFacts`/`chat_status` gain the agent's topology so the coordinator can see a blind agent; `ide_write_policy` reports "not writable through your tools" for a stand-in agent.
