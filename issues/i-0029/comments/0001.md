i-0029 environment, 2026-09-16: **mechanism confirmed, and it is the second candidate — the failed first spawn is a red herring.**

The evidence is in this environment's own transcript, first line, put there before my first turn:

```
[note] Claude Code does not offer a model "opus" — it advertises ["default", "opus[1m]",
"sonnet", "sonnet[1m]", "haiku", "claude-fable-5-1[1m]"], and this chat is on its default
```

So `fable` was not an advertised id, and neither is `opus`; `opus[1m]` and `sonnet` are. The refusal DID run, in `Chats::create_orchestrated`'s `on_ready_once` hook (`chats.rs:953`), and it wrote a note into the sub-chat's own transcript — a surface the coordinator never reads. Nothing was said to the caller.

The first candidate is refuted by a case the issue already contains. i-0026 was started with `sonnet` and its first spawn died too (it is in i-0011's own list of five: i-0022, i-0023, i-0025, i-0026, i-0028), and `chat_status` has reported `sonnet` ever since. A value the agent advertises survives a failed first spawn; `model_value` is a plain cell that neither `Closed`, `reset_session(false)` nor `ensure_client` touches. What it does not survive is `build_model_controls`'s stale check (`chat.rs:6828`), which silently drops any value the session does not advertise.

**The promise is structurally unreachable for `issue_start`.** docs/ENVIRONMENTS.md says "an unknown id is refused by naming the advertised ones, and the chat is left created and *unprompted*". That path exists — `chats.rs:978` — but it only runs when the pane is NOT waiting for its container. Outside the primary the container always starts first (`hold_for_container`), so `issue_start` always takes the `awaiting_container()` branch at `chats.rs:950`, which answers `Ok` immediately with `model: <whatever was asked for>` because it will not hold a tool call open for a container build. By the time the truth is known the brief has been sent and the tool call is long finished. Three consequences, all seen: `chat_status` reads `null`, the issue record says `model: "opus"` (server.rs:2942 records `created.model`, the wish), and the chat runs the default.

**Where the fix goes: not the reconnect path.** i-0011 can have `chat.rs`'s connection code to itself — I need nothing there. The change lives where the value is held and where the answer is composed:

- one pure `resolve_model(wanted, advertised, current) -> InForce | Refused | Default` in `chat.rs` beside `model_choices`, used by both `build_model_controls` (which applies it) and `create_orchestrated` (which reports it), so the two cannot disagree again;
- the pane records the outcome, so `ChatFacts` can separate "the model this session is running" from "a choice no session has confirmed yet" from "a choice the session refused, and the ids it advertises" — the issue's second bullet;
- `CreatedChat`/`issue_start` stop reporting an unconfirmed wish as `model`, and say in the note that `chat_status` is where the confirmed answer lands;
- the `model` tool description and the ENVIRONMENTS paragraph get corrected to what the code can actually promise.

One thing found along the way, not widened into here and filed separately if you want it: `advertised_models` is recorded only at `Ready`, so an agent that revises its model list mid-session (`ConfigOptionUpdate`, `chat.rs:7146`) leaves it stale. I am moving that one assignment into `build_controls`, which both paths call, because the new code reads it — say the word if you would rather have it as its own issue.
