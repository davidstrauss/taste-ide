Fixed in `640b1c0` on `agents/i-0011`. The rule the branch establishes is one sentence: **a prompt the IDE accepted is never dropped.**

**What was actually wrong.** `submit_prompt` — the path every prompt that does not come from the composer takes, including `issue_start`'s brief — refused outright when the chat had no live agent. Outside the user's own environment "no live agent yet" is the *normal* state of a chat `issue_start` has just made, because `b85b8ac` deliberately holds the agent back for its container. So the ordering that commit built was half-built: the gate held the agent and nothing held the prompt, and the tool's description promised the opposite.

Three seams had to hold and each was open:

1. **The hold.** `chat::delivery` decides `Send` / `Hold` / `Refuse`. It holds only when something is *already* on its way and starts nothing itself — which is what keeps `chat_send` outside the environment cap (the comment above `chat_send` in server.rs now says so explicitly). It still refuses when nothing is coming, because a prompt held for an agent nobody is bringing up reads as dispatched and never runs, which is the same failure wearing a nicer answer.
2. **The orphan.** A prompt already handed to a process that then dies took that process's fate. A typed one goes back to the composer; one nobody typed had no box to go back to and simply evaporated — which is exactly what the 255 exec refusal produces. It goes back on the hold queue now (`chat::Unfinished`). Only prompts whose turn never ended, so what can be repeated is a turn that did not get through.
3. **The retry.** A chat whose agent died before its first `Ready` has no session id, and `schedule_reconnect` read that as "the user ended this conversation" and stayed quiet forever. It now asks whether anything is *owed* — a held prompt, or somebody waiting on that first `Ready` — and reconnects on a fresh session when something is. The queue drains at both ends of the wait: the environment settling, and the session reaching `Ready`.

**The tools stop making the coordinator guess.** `held` on `chat_send` and `issue_start` separates "waiting behind a turn" from "no agent has it yet"; `chat_status` carries `held_prompts`. That last one matters: a chat holding its brief has no process, so it reads `disconnected`, and "a chat that stays here needs a person" is precisely the wrong instruction for one waiting on podman. The note now says so and tells the caller not to re-send.

**The test.** `the_first_prompt_survives_a_container_slow_to_accept_an_exec` walks this issue's own log — container starting, brief arriving mid-wait, the exec refused, the process gone before `Ready`, the respawn — because the defect is the *sequence*: every answer was locally defensible and the message vanished between them. `a_prompt_is_held_only_when_something_is_bringing_an_agent_up` is exhaustive over the eight states and pins the rule underneath. Both are pure-function tests in the shape `b85b8ac` chose for `container_gate`, which is what the crate can gate on headlessly.

**Gate.** `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets -- -D warnings` clean; `taste-app` 152 passed, `taste-mcp` 65 passed, `taste-acp` 71 passed, `taste-git` 77 passed. Not visual, so no probe.
