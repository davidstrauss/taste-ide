Done and published as a checkpoint on `agents/i-0013` (c6a6321). Gate green: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` (the whole workspace passes; taste-core's `watcher` and taste-devcontainer's `configwatch` tests fail intermittently on this host when many run in parallel, because `fs.inotify.max_user_instances` is exhausted by the desktop session plus the fleet — they fail identically on the pristine tree and pass in isolation).

What changed:

- `SupervisorState::holds_a_container` (running, building, or starting) is the predicate, and `stop_wanted` now reads it too rather than spelling the same triple a second time.
- The cap counts non-primary environments holding a container, read off the supervisors rather than the fleet snapshot: the fleet is a round trip to the window that legitimately fails when no window is attached, and a gate that stops counting when nobody is looking is not a gate. It is the same fact one hop earlier — the fleet's own `state` is derived from these supervisors — and touches no podman.
- **The restart path is `devcontainer_reload`, and it is now gated too.** It is the only tool that can bring a stopped environment back up; `chat_send` cannot, because revival is `chat::revive_wanted` with `user_initiated: true` and `ChatPane::send` is its only caller — an orchestrated send goes through `submit_prompt`, which answers "no live agent" and leaves the container down. That is stated in a comment where `chat_send` is dispatched. The reload gate is narrowed twice: it does not fire for an environment that already holds a container (the ordinary repair loop), and never for the primary.
- `issue_list` reports `running` against `cap`, with `environments` (clones on disk) beside it. Both come off the registry, so they agree with the gate and do not read as zero when the fleet is unknown. Its refusal also stopped pointing at `env_list`, a tool folded into `issue_list` some time ago.
- Tests: the cap test now builds environments that are actually running (one of each counting state); a sibling asserts a start succeeds with the cap's worth present but stopped or failed, which also pins the dispatch order; a third pins the reload gate from both sides. `SupervisorState::set_state_for_tests` is the seam.

**Open question, still open:** nothing bounds total clones on disk now. The code says it was considered and left, with a note that a looser ceiling is the number to add if one is ever wanted. Say the word and it changes.
