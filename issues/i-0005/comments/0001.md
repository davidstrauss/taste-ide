Declined. The mechanical cause this was filed about is fixed on main, and the want that replaced it is a different question that this issue's framing does not hold.

What shipped: `0f19aa7` ("Every IDE tool says what it does to the world, so a listing stops asking permission", 2026-09-08 09:00). All 37 IDE tools carried no MCP annotations, and the spec's defaults for an unannotated tool are `readOnlyHint: false` and `destructiveHint: true` — so `issue_list`, a read of a git ref, presented itself as a possibly-destructive mutation, and a client set to run reads without asking was right to stop and ask. `protocol::effect` now classifies them: 28 reads, 7 writes, and 2 that always ask (`ide_exec`, the only tool with `openWorldHint`, and `devcontainer_reload`). The fallback stays `Destructive`, and `every_tool_says_what_it_does` walks the served list so an unclassified tool cannot be waved through.

What that leaves, and why it is not this issue: David, 2026-09-08 — "I'm not actually trying to turn on the 'always approve' option… What I'm actually trying to do is have the AI-based auto-approve, analyze the requests and decide." Annotations tell a client what a call does; they do not judge a particular call. `0f19aa7`'s own closing paragraph names the remaining lever as the IDE answering these itself, "a decision about a consent surface rather than a bug fix." That design question is not recorded on the backlog anywhere, and it is not recorded by this issue either — the open question under it is whether the judge decides autonomously inside a policy set once, or only filters what is worth interrupting for and escalates the rest.

Never started, so no environment and no branch: nothing is stranded by this close.
